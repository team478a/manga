# MANGAI UI刷新計画（UI Redesign Plan）

作成日: 2026-07-26（Phase D0.5追記: 同日）
状態: **調査完了（Phase D0承認済み）。Phase D0.5（ビジュアル方針確定）着手中、コード変更なし**。実装は、保守性改善stackの統合方針とビジュアル仕様の両方が承認されてから、統合済み基準ブランチ上の新しい実装ブランチで開始する。

本ブランチ（`design/mangai-ui-refresh`）は`handoff/codex-to-claude-20260725`から分岐しており、最新の`feature/manga-canvas-mvp`とも乖離しているため、**本ブランチではUIコード・CSS・Tailwind設定・Reactコンポーネントの実装を行わない**。Phase D0.5を含め、実装着手までは文書更新のみを行う。

前提文書: [`CURRENT_UI_AUDIT.md`](CURRENT_UI_AUDIT.md)（現状監査）、[`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md)（トークン・コンポーネント案）、[`SCREEN_INVENTORY.md`](SCREEN_INVENTORY.md)（画面一覧）、[`DESKTOP_CREATIVE_STUDIO_SPEC.md`](DESKTOP_CREATIVE_STUDIO_SPEC.md)（「MANGAI Creative Studio」4画面詳細ビジュアル仕様・Phase D0.5の正本）

## 1. 本計画のスコープと非スコープ

### スコープ（実施する）

- 見た目・UIコンポーネント構造の刷新（デザイントークン適用、共有コンポーネント抽出、God Componentの画面表示層のみの分割）

### 非スコープ（実施しない・変更禁止）

`CURRENT_UI_AUDIT.md`§8と同一。再掲:

- ビジネスロジック、API/DB/Storage/Desktop IPC契約
- Canvas保存処理（revision競合、autosave再試行ロジック）
- AI生成ルーティング（Generation Router、safe/adult分類、fail-closed判定）
- 認証・決済処理
- 機能削除

画面のリファクタリングでロジックを含むファイルを分割する場合も、**ロジック（state管理・API呼び出し・バリデーション）とビュー（JSX/見た目）を分離するだけ**とし、ロジックの挙動そのものは変更しない。挙動変更が必要になった場合は本計画を止め、責任者に確認する。

## 2. 画面ごとの変更優先順位

優先順位は「God Component化の深刻度」「ユーザー接触頻度」「変更リスク（ビジネスロジック密結合度）」の3軸で判定。**リスクが高い画面ほど後回し**にする（先に低リスク・高頻度の画面でコンポーネントライブラリを確立し、そのうえでリスクの高いCanvas Editor等に適用する）。

### Desktop

| 優先度 | 画面 | 理由 |
| --- | --- | --- |
| P1 | 共有コンポーネント基盤（Button/Modal/Card/FormField/EmptyState） | すべての画面変更の前提。ここが確立しないと各画面の刷新が重複作業になる |
| P1 | Global Nav / App Header / Status Bar（シェル） | 全画面共通シェル。他画面への影響が最も大きく、最初に統一すべき |
| P2 | Project一覧（Home） | 高頻度接触、ロジックが比較的軽い（Project CRUD中心） |
| P2 | 新規Project modal | Modal共通化の実証実装として適する |
| P2 | Export Dialog | 既存実装の完成度が高く、Modal共通化のリファレンス実装に使える |
| P3 | Character Profile Manager / Project Generation Policy Settings | 中規模、ロジックとビューの分離がしやすい |
| P3 | Settings（AISettings/DezgoSettings/AdultGenerationSettings） | `SettingsShell`の新設と合わせて刷新。ロジック（provider設定の保存）は変更しない |
| P4 | Hub連携（HubStatus） | 端末認証フローに触れるため慎重に。表示層のみ分離 |
| P4 | Creator Chat | チャットの型安全性（`any[]`）に手を入れたくなる誘惑があるが、本フェーズでは見た目のみ |
| P5 | Workspace Status Controls / 画像生成Job（GenerationJobs） | Job状態・外部dispatch確認等、ロジック密結合度が高い。P1〜P4で確立したパターンを適用する形で最後に着手 |
| P6 | **Manga Canvas Editor** | 最大リスク・最大規模。Canvas保存処理・Konva描画に触れずツールバー/プロパティパネルのUIのみ段階的に分離する。最後に着手し、他画面よりも小さい単位（ツールバーのみ→プロパティパネルのみ→レイヤーUIのみ）でPRを分割する |

### Hub

| 優先度 | 画面 | 理由 |
| --- | --- | --- |
| P1 | 共有コンポーネント基盤（Button/Card/FormField/PageHeader/FlashMessage/EmptyState/StatusPill） | Desktopと同様、前提基盤 |
| P1 | 区画別layout.tsx新設（`dashboard/layout.tsx`、`admin/layout.tsx`） | adminナビ不在という機能的な穴を埋めつつ、以降の画面刷新のシェルを用意する |
| P2 | 公開マーケットプレイス（`/`、`/works`、`/works/[id]`） | 最も外部露出が高く、SEO/第一印象に直結。ロジックが軽い（読み取り中心） |
| P2 | 認証画面（`/login`、`/signup`） | 小規模、高頻度、リスク低 |
| P3 | Dashboard一覧系（works/products/sales/purchases/goods-requests） | `RowCard`/`DataTable`/`PageHeader`の実証実装 |
| P3 | Checkoutフロー（`/checkout/*`） | `ResultPanel`共通化。決済ロジックには触れず表示のみ |
| P4 | Dashboard詳細/フォーム系（works/new・edit、products/new・edit、billing、devices） | `FormField`適用 |
| P4 | Admin一覧系（users/works/products/orders/goods-requests） | Dashboard一覧系のパターンを流用 |
| P5 | `admin/cloud-ai` | 品質劣化が著しく、UI刷新の前に型・構造の最低限の整理（ロジック変更なし、コンポーネント分割のみ）が必要。単独タスクとして扱う |
| P5 | `SalesPackageImport.tsx` | 493行のGod Component。ZIP検証ロジックとビューの分離が前提 |
| P6 | **Cloud Canvas Editor** | Desktop Canvas同様、最大リスク。二重ヘッダー問題の解消（レイアウト統合）を含めて最後に、最小単位で段階着手 |

### Phase D0.5: ビジュアル方針確定（現在のフェーズ・コード変更なし）

**目的**: Phase D1以降でコードへ反映する前に、MANGAI Desktopの中核3画面（Project一覧／制作ワークスペース／設定画面）のビジュアル仕様を文書として確定する。本フェーズはコード変更を一切行わない。ワイヤーフレーム・仕様の承認を得てからPhase D1（トークン導入）へ進む。

**前提となる暫定方針（責任者指示、2026-07-26）**:

- Desktopを最優先する。Hubのデザイン実装はDesktopの基本デザイン確定後に行う。
- ダークテーマを維持する（`CURRENT_UI_AUDIT.md`で確認済みの`:root { color-scheme: dark; }`、`forced-colors`対応を継続）。
- 紫系アクセント（現行`--accent: #6848d8`系統）を維持する。`DESIGN_SYSTEM.md`§5「未決事項1」（Desktop/Hubブランドカラー統一の要否）は本方針により**Desktop側は現状維持で確定**、Hub側は引き続き未決事項として残る。
- Adobe系制作ツール（Photoshop/Clip Studio Paint等）が持つ専門性の高い密度の高いUIと、初心者でも迷わない分かりやすさを両立する。
- 画面構成は「左＝構成・素材」「中央＝Canvas」「右＝プロパティ・レイヤー・AI」の3カラムを維持する（既存の`ProjectPanel`／`MangaCanvas`／`InspectorPanel`の役割分担を踏襲）。
- 上部に現在地表示と主要操作、下部に保存・接続・生成状態を配置する（既存の`AppHeader`／`StatusBar`の役割分担を踏襲）。
- DesktopをTailwindへ移行しない。既存のプレーンCSS＋CSS変数（`styles.css`）の技術基盤を維持する。
- Hubのデザイン実装はDesktop確定後に着手する（本フェーズの対象外）。
- DesktopとHubはコードを共有せず、`DESIGN_SYSTEM.md`のトークン名・コンポーネントAPI設計のみを共通化する。

以降、対象3画面それぞれについて、ワイヤーフレーム／各領域の役割／主操作と副操作の優先順位／初回利用者の制作フロー／コンポーネント仕様／レスポンシブ配置／状態別仕様／アクセシビリティ要件を定義する（**この3画面分は初回イテレーションとして以下に残す**）。

**主操作と副操作の優先順位**

1. **主操作（最優先・最も強い視覚重み）**: 「＋新規Project」ボタン（`Button variant="primary"`）、既存Projectカードの「開く」
2. **副操作**: 言語切替、更新チャンネル確認、自動バックアップの手動実行

**初回利用者の制作フロー**

1. 初回起動時、Project一覧は空状態（§状態別仕様参照）となり、「＋新規Project」がひときわ強調表示される
2. 新規Project作成モーダルで最小限の入力（タイトル、読み方向、Canvasサイズプリセット）のみを必須とし、詳細設定は折りたたみで隠す（初心者は最短でCanvasへ到達できることを優先）
3. 作成後は自動的に制作ワークスペースへ遷移する（現状の挙動を維持、UIのみ整理）

**コンポーネント仕様**

- **ボタン**: `Button variant="primary"`（新規Project、accent色背景）、`Button variant="secondary"`（今すぐ実行等）。サイズは`md`を標準とする。
- **カード**: `Card variant="interactive"`（hover時にわずかな浮き上がり、`--shadow-panel`使用、クリックでProjectを開く）。カード内の情報密度は「代表画像＋作品名＋最終編集日＋開くボタン」の4要素に固定し、それ以上詰め込まない（Adobe系ツールの密度の高さは制作ワークスペース側で表現し、Home画面は簡潔さを優先）。
- **フォーム**（新規Projectモーダル）: `FormField`（label+input）。必須項目には視覚的な必須マーク、エラーはフィールド直下に赤系（`--danger`）で表示。
- **ステータス表示**: 自動バックアップ状態は`StatusBadge`の5トーン（neutral/info/success/warning/danger）を使用。「正常」は`success`、進行中は`info`、失敗は`danger`。

**レスポンシブ配置**

| 解像度 | Project cardグリッド列数 | 備考 |
| --- | --- | --- |
| 1920×1080 | 4列 | カード幅は余白込みで約440px |
| 1366×768 | 3列 | カード幅を保ちつつ列数を減らす。文字サイズは変更しない |

**狭幅時の左右パネル動作**: Home画面には左右パネルが存在しないため対象外（制作ワークスペースのみ該当）。

**長い作品名・空状態・エラー状態・生成中状態**

- **長い作品名**: カード内でCSSの`text-overflow: ellipsis`により1行で省略し、`title`属性またはtooltipで全文を表示する。2行折返しは採用しない（カードの高さが不揃いになるのを防ぐ）。
- **空状態**（Project未作成）: 中央に説明文＋「＋新規Project」ボタンを大きく配置する`EmptyState`コンポーネントを使用。既存`home.none`i18nキーの文言を維持。
- **エラー状態**（Project読み込み失敗、DB破損等）: 画面上部に`role="alert"`のエラーバナー（既存実装を維持、見た目のみ`FlashMessage`相当へ統一）。自動リカバリー機能（既存の`backups/recovery/`隔離＋再構築）が働いた場合はその結果を状態バナーに表示。
- **生成中状態**: Home画面自体に生成中表示はなし（生成はProject内のGenerationJobsが担当）。ただし自動バックアップ実行中は状態バナーが`info`トーンで進行を示す。

- 既存の`.skip-link`（`a11y.skipMain`）を維持し、`#main-content`へジャンプできること
- Project cardは`<article>`＋見出し要素の組み合わせとし、カード全体をクリック可能にする場合もキーボードから`Tab`＋`Enter`で到達・実行できること
- 新規Projectボタンとカードグリッドのフォーカス順序が視覚順序と一致すること
- `forced-colors`（Windows High Contrast）で、カード境界線・選択状態が`CanvasText`/`Highlight`で可視であること（既存の`@media (forced-colors: active)`実装を維持）
- コントラスト比: 本文文字と背景で4.5:1以上、大きい文字（見出し等）で3:1以上（WCAG AA準拠、ダークテーマの`--text-primary`／`--bg-app`の組み合わせで確認する）

3. **副操作**: 「レイアウト」「表示」メニュー、Inspectorタブ切替、左パネルでのPage切替
4. **三次操作**: Undo/Redo、インポート/書き出し（頻度は高いが、主作業を妨げない位置＝ヘッダーへ配置）
5. **文脈操作**: 選択オブジェクトに応じたプロパティ編集（右パネル、選択が変わるたびに内容が切り替わる）

**初回利用者の制作フロー**

1. Project作成直後、Canvasは既定テンプレート（既存の6ページテンプレート等）が適用された状態、または空のPage 1が表示される
2. 左パネルはAsset一覧が空のため「素材をドラッグ&ドロップ、またはクリックして追加」という案内を表示（既存の空状態パターンを踏襲）
3. ツールバー「追加」メニューを開くと、コマ・吹き出し・テキストの追加候補がテンプレート付きで提示される（Adobe系ツール利用者には「見慣れた場所にツールがある」、初心者には「迷ったら追加メニューを開けばよい」という一貫した導線）
4. 右パネルは初期状態でPropertiesタブを表示し、何も選択されていない場合は「コマや吹き出しを選択するとここに設定が表示されます」という案内を表示する
5. AIタブ（Creator Chat埋め込み）は制作の任意工程として、強制せずいつでも呼び出せる位置に留める

**コンポーネント仕様**

- **ボタン**: ツールバーの各メニューは`CanvasToolMenu`（既存）をベースに、`Button`トークンへ色・余白を統一。主操作系ボタン（追加）は`variant="primary"`寄りの視覚重み、レイアウト/表示は`variant="secondary"`寄り。
- **カード**: 左パネルのAsset一覧・Page一覧サムネイルは`Card variant="default"`（薄い境界線、hoverで`--bg-hover`）。選択中は`--bg-selected`。
- **フォーム**: 右パネルのプロパティ編集（座標・サイズ・色等の数値入力）は`FormField`の中でも高密度なインライン版（ラベルを左、入力を右に横並び）を新設し、Adobe系ツールに近い密度を再現する。Home画面のフォームとは異なる密度仕様を許容する（§コンポーネント仕様の製品内バリエーションとして`DESIGN_SYSTEM.md`に追記予定）。
- **ステータス表示**: 保存状態（`savingTone()`が返すneutral/info/success/danger）、接続状態（`connectionTone()`）、生成Job数バッジはすべて`StatusBadge`の5トーンに統一。

**レスポンシブ配置（1366×768 と 1920×1080）**

| --- | --- | --- |
| 左パネル幅 | 260px（既定） | 260px（既定、1200px未満で250pxへ縮小する既存挙動を維持。1366pxは1365px境界のすぐ上のため、境界付近の挙動を実機で要確認） |

**狭幅時の左右パネル動作**（既存実装を踏襲、見た目のみ整理対象）

**長い作品名・空状態・エラー状態・生成中状態**

- **空状態**: Asset未登録時の左パネル、Page内要素が0件の場合のCanvas（「追加メニューから開始してください」という案内オーバーレイ）。
- **エラー状態**: Canvas保存失敗（revision競合等）は`role="alert"`バナーをヘッダー直下に表示し、既存の再試行ロジック（`useCanvasAutosave.ts`相当、Desktop版）の結果を反映。エラー内容は`domain-errors`相当の安全なメッセージのみ表示し、DBの生エラーは表示しない。

**アクセシビリティ要件**

- `GlobalNav`は既存の`nav.main`（aria-label）を維持
- `InspectorPanel`のタブは既存`Tabs.tsx`のARIA tablist実装（roving tabindex、Arrow/Home/End）を維持・全面採用する
- Canvas上のオブジェクト選択・操作はマウス操作が主だが、既存のキーボードショートカット（Undo/Redo等）を維持し、新規追加するUI要素（ツールバーメニュー等）にも`aria-label`／`aria-expanded`を付与する
- 右パネルのプロパティフォームは高密度になるため、各入力に明示的な`<label>`（視覚的に小さくてもDOM上は存在させる）を維持し、スクリーンリーダーで「何を編集しているか」が常に分かるようにする
- `forced-colors`対応（既存の境界線・選択状態の強制表示）を全パネルで維持

## 5. ロールバック方法

1. 各フェーズ・各画面のPRは小さく保ち、1PR = 1画面（またはCanvas Editorのように1機能単位）とする。問題発生時は該当PRのみをrevertすれば良い状態を維持する。
2. 共有コンポーネント（Phase D2）は、既存画面が新コンポーネントへ切り替わるまで**並行して旧実装を残す**（例: 旧`.panel-lite`クラスは残したまま新`Card`コンポーネントを追加し、画面ごとの移行が終わった後にのみ旧CSSクラスを削除する）。これにより、移行途中の画面で問題が出ても新コンポーネント側だけをrevertできる。
3. デザイントークン導入（Phase D1）は、CSS変数/Tailwind theme拡張のみの変更とし、既存のセレクタ・クラス名は変更しない。値を旧に戻すだけで即座にロールバックできる。
4. Canvas Editor（Phase D6）のように保存処理に近い画面は、機能フラグ的な分離が難しい場合、**該当PRのブランチをmainへmergeする前に、Desktop実機での動作確認と`desktop:test`全件成功を必須条件とする**。
5. 各PRのコミットメッセージに変更対象画面と非スコープ遵守を明記し、`docs/design/`配下（または責任者が指定する進捗記録先）に実施結果を記録する。
